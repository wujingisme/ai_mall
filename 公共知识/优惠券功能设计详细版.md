# AI Mall 优惠券功能设计详细版

## 1. 一句话概括

优惠券采用“模板定义规则、用户券承载权益、发放记录负责审计、分享记录负责传播、订单模块负责核销”的分层设计。先完成模板和发券，再扩展分享，最后接入订单，避免一次性引入过多状态和一致性风险。

## 2. 功能范围与批次

| 模块 | 当前状态 | 说明 |
| --- | --- | --- |
| 模板管理 | 后端已完成 | 创建、分页查询、详情、草稿修改、启用、停用 |
| 人工发券 | 已完成 | 管理员向 CUSTOMER 用户发放，支持幂等和审计 |
| 我的优惠券 | 已完成 | 用户只能通过 JWT 查询自己的优惠券 |
| 分享领取 | 代码已完成，待环境验收 | 随机凭证、预览、登录领取、本人禁止领取 |
| 新用户自动发券 | 未开始 | 微信用户首次创建时由后端触发 |
| 订单抵扣 | 等订单模块 | 锁券、核销、取消返还和退款处理 |

## 3. 核心领域模型

```text
CouponTemplate  1 ─── N  CouponGrant  1 ─── N  UserCoupon
       │                         │
       └────────────── N  CouponShare ─── N  CouponClaim
```

### 3.1 coupon_template：优惠券模板

模板是规则集合，不代表某个用户已经拥有优惠券。主要字段包括名称、券类型、使用门槛、优惠金额、总发行量、已发行量、每人限领数量、有效期类型和状态。

状态通常为 `DRAFT → ACTIVE → INACTIVE`。草稿允许完整修改；启用后核心金额、门槛和有效期规则锁定；停用阻止继续发放，但不自动作废已发出的用户券。

### 3.2 coupon_grant：发放审计

记录谁在什么时间、因为什么原因、向哪个用户发了多少张券。保存模板、目标用户、操作人、请求数量、成功数量、原因、幂等键和结果状态。它既是审计记录，也是重复请求返回原结果的依据。

### 3.3 user_coupon：用户实际权益

一行代表用户拥有的一张优惠券。除了用户和模板关联，还保存名称、门槛、优惠金额、有效期等规则快照。这样即使模板之后停用或规则发生变化，已经发出的权益仍能按发放时规则解释。

状态包括 `UNUSED`、`USED`、`EXPIRED`、`VOID` 等，过期状态可依据 `valid_until` 实时推导，不必依赖定时任务批量改库。

### 3.4 coupon_share / coupon_claim：分享与领取

分享链接只携带不可猜的随机 `shareToken`。数据库保存 token 的哈希，不保存明文凭证。解析接口只返回展示预览；真正领取时，后端重新校验分享状态、模板状态、有效期、库存、用户限领和本人领取限制。领取记录通过唯一约束防止同一用户重复领取同一分享。

## 4. 管理员发券请求链路

```text
Admin UI
  → POST /api/v1/admin/coupon-grants
  → Spring Security 验证管理员权限
  → @Valid 校验请求字段
  → CouponGrantService.grant()
  → coupon_grant / user_coupon
```

请求至少包含 `templateId`、`targetUserId`、`quantity`、`reason` 和 `idempotencyKey`。数量限制为 1 到 100，幂等键只允许字母、数字、下划线和短横线。

Service 的关键顺序如下：

1. 先按幂等键查询历史发放记录。
2. 已存在且核心参数一致，直接返回历史结果。
3. 已存在但参数不同，返回冲突，防止幂等键被挪用。
4. 校验目标用户存在、启用且具有 `CUSTOMER` 角色。
5. 查询优惠券模板。
6. 使用条件 UPDATE 原子预占发行量。
7. 统计目标用户已有数量并检查每人限领。
8. 插入发放审计记录。
9. 按数量创建用户券，并复制规则快照。
10. 所有步骤成功后提交事务，返回 201。

## 5. 事务、幂等与并发

### 5.1 事务边界

发券方法使用事务包住库存预占、审计插入和用户券插入。限领校验失败、唯一键冲突或任意写入异常，都会回滚之前的库存变更，避免出现“库存扣了但没有发券”的半成功状态。

### 5.2 幂等策略

幂等键对应一次业务请求，而不是一次网络连接。重试时，如果模板、用户、操作人和数量都一致，则返回原发放记录；如果参数不一致，则拒绝请求。数据库唯一索引是最后一道并发保护，Service 逻辑负责给出可理解的业务错误。

### 5.3 防止库存超发

库存使用条件更新：只有模板为 `ACTIVE`、未过期且 `issued_quantity + quantity <= total_quantity` 时才允许更新。通过检查受影响行数是否为 1 判断预占成功。数据库在同一条 SQL 中完成判断和加库存，避免“先查询、后更新”之间的竞态窗口。

### 5.4 防止单用户超限

模板库存预占后再统计该用户已领取数量。如果超过 `per_user_limit`，抛出冲突异常并回滚整个事务，因此库存不会被错误消耗。大规模场景下可以进一步增加按用户维度的计数表或唯一约束，但必须保持与现有快照和审计语义一致。

## 6. 安全边界

- 管理员接口由 Spring Security 做角色授权，前端路由隐藏不能替代后端权限。
- 当前用户优惠券接口从 JWT 身份取得 userId，不接受前端传入的任意用户编号。
- 分享链接不放 OpenID、用户 ID、优惠券码或 AppSecret。
- 分享凭证使用安全随机值，数据库只保存哈希，便于撤销和审计。
- 金额由后端使用字符串接收并转换为 `BigDecimal`，避免前端浮点误差。
- 最终订单优惠金额必须由后端根据订单和优惠券快照重新计算，不能信任前端提交的结果。

## 7. 接口分层

### 模板管理

```http
POST /api/v1/admin/coupon-templates
GET  /api/v1/admin/coupon-templates
GET  /api/v1/admin/coupon-templates/{id}
PUT  /api/v1/admin/coupon-templates/{id}
POST /api/v1/admin/coupon-templates/{id}/activation
POST /api/v1/admin/coupon-templates/{id}/deactivation
```

### 发放与用户查询

```http
POST /api/v1/admin/coupon-grants
GET  /api/v1/me/coupons
GET  /api/v1/me/coupons/{id}
```

### 分享与领取

```http
POST /api/v1/me/coupon-shares
POST /api/v1/coupon-shares/resolve
POST /api/v1/coupon-claims
```

最终接口契约以 `api/openapi.yaml` 为准；接口名称或字段变化时，必须同步 TypeScript 类型和客户端。

## 8. 典型失败场景

| 场景 | 后端行为 | 设计目的 |
| --- | --- | --- |
| 重复提交同一请求 | 返回原发放结果 | 保证幂等 |
| 幂等键换参数 | 409 冲突 | 防止请求串单 |
| 模板停用或过期 | 条件更新失败 | 后端权威判断 |
| 库存不足 | 条件更新失败 | 防止超发 |
| 用户超过限领 | 回滚事务并返回 409 | 不消耗库存 |
| 分享人领取自己的分享 | 拒绝领取 | 防止规则绕过 |
| 同一用户重复领取 | 唯一约束或业务冲突 | 防重复发券 |

## 9. 测试与验收

本地先用两个商城测试账号验证业务，不依赖真实微信账号。重点覆盖模板状态、空库存、过期模板、重复请求、参数冲突、本人领取、重复领取、限领和并发领取。分享领取最终再使用两个真实微信账号完成真机验收。

部署验收时还要确认真机不能访问电脑的 `127.0.0.1`，必须使用可访问的 HTTPS 后端和微信合法请求域名。

## 10. 面试问答

### Q1：为什么要把优惠券模板和用户优惠券分开？

模板描述一批券的公共规则，用户券表示某个用户实际拥有的一张权益。分离后可以统一管理库存，也可以保存发放时的规则快照，避免模板修改影响历史权益。

### Q2：如何保证重复点击不会重复发券？

客户端提交幂等键，服务端先查 `coupon_grant`。同键同参数直接返回历史结果；同键不同参数返回冲突；数据库唯一索引作为并发下的最终保护。

### Q3：为什么库存不能先查询再更新？

先查询再更新存在竞态窗口，两个请求可能同时看到相同剩余量。条件 UPDATE 把资格判断和数量增加合并成原子操作，并通过受影响行数判断是否成功。

### Q4：为什么限领检查失败后库存不会被消耗？

预占库存、限领校验、审计记录和用户券写入都在同一事务中。抛出业务异常后事务回滚，库存更新也随之撤销。

### Q5：为什么分享链接不用 JWT？

分享凭证是一次业务资源标识，需要支持失效、限次、领取记录和审计。随机 token 配合数据库哈希比 JWT 更容易撤销和控制生命周期。

### Q6：为什么订单金额不能由前端计算后直接提交？

前端数据可被篡改。订单服务应在后端读取用户券快照，重新检查用户归属、有效期、门槛和状态，再计算优惠金额并锁定或核销。

## 11. 当前设计的优缺点

优点是职责边界清晰、审计完整、支持幂等和并发控制，并且可以逐步扩展新人券、批量任务和订单核销。缺点是领域表较多，事务、唯一索引和状态迁移需要严格维护；大规模批量发券后续可能需要异步任务和监控。

## 12. 推荐面试表达

> 我把优惠券拆成模板和用户实例：模板管理规则与库存，用户券保存发放时的不可变快照，发放记录负责审计和幂等。并发发券时用条件更新原子预占库存，再在同一事务中检查用户限领、写审计和创建用户券。分享只携带随机凭证，所有资格由后端重新校验。订单核销暂时延后到订单模块，避免跨模块过早耦合。
