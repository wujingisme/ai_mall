# AI Mall 后端代码阅读手册

这份手册面向熟悉 Vue/React、但第一次阅读 Java/Spring 后端的前端开发者。目标不是让你一次记住所有 Java 语法，而是让你知道：一个前端请求进入后端以后，依次经过哪些文件、每一层负责什么、应该先读哪里、出现问题时如何定位。

## 1. 先建立一个前端类比

可以把一次后端请求想成下面这条链路：

```text
页面/小程序
  -> request.ts 发出 HTTP 请求
  -> Controller 接收路径、参数和登录身份
  -> DTO 校验请求体
  -> Service 编排业务规则和事务
  -> Mapper 把对象转换成 SQL 并访问 MySQL
  -> Entity 对应数据库表的一行
  -> Service 把 Entity 转成 VO
  -> Controller 返回 JSON
```

前端常见的对应关系如下：

| 前端概念 | 后端对应物 | 作用 |
| --- | --- | --- |
| 路由页面/接口文件 | Controller | 定义 URL 和 HTTP 方法 |
| TypeScript 请求类型 | DTO | 接收并校验客户端输入 |
| composable/store 中的业务流程 | Service | 组织业务规则、事务和多个表的操作 |
| API client | Mapper | 访问数据库，执行查询或更新 |
| 数据库表类型 | Entity | 描述表字段与 Java 属性的映射 |
| 返回给组件的类型 | VO/Response | 控制真正暴露给客户端的字段 |
| Axios 响应拦截器 | GlobalExceptionHandler | 把异常统一转换成 HTTP 错误 JSON |
| 路由守卫 | SecurityConfig + JWT Filter | 在服务端强制执行认证和权限 |

## 2. 阅读代码时的推荐顺序

不要从 `MallApplication` 之后随机点文件。建议固定按下面的顺序阅读。

### 第一步：先看需求和接口契约

先看仓库根目录的 `功能设计方案.md`、`api/openapi.yaml` 和 `database/schema.sql`。

- 设计文档告诉你业务为什么存在，以及状态如何变化。
- OpenAPI 告诉你 URL、请求字段、响应字段和错误码。
- SQL 告诉你数据最终怎样保存，唯一键和检查约束在哪里。

例如“人工发券”不是简单插入一条券：它需要操作人、目标用户、幂等键、模板库存、用户限领和用户优惠券快照。因此后面要同时阅读 `CouponGrantController`、`CouponGrantService`、`CouponGrantMapper`、`CouponGrant`、`UserCoupon` 和对应数据库表。

### 第二步：从 Controller 找到入口

Controller 只做三件事：

1. 用注解声明路径，例如 `@PostMapping("/login")`。
2. 接收路径参数、查询参数、请求体和 `Authentication`。
3. 调用 Service 并返回结果。

Controller 不应该相信前端传来的用户 ID 来决定数据归属。当前用户 ID 应该从已经通过 JWT 校验的 `Authentication` 中取得。比如 `UserCouponController` 的“我的优惠券”使用 JWT 主体作为 `userId`，这样用户无法改请求参数读取别人的券。

看到一个 Controller 方法时，按这四个问题阅读：

- 它对应哪个 HTTP 方法和 URL？
- 参数来自 `@RequestBody`、`@PathVariable`、`@RequestParam` 还是登录上下文？
- 调用了哪个 Service 方法？
- 哪些异常会被全局异常处理器转换成什么状态码？

### 第三步：再看 DTO，确认输入边界

DTO 是“客户端输入的白名单”。例如 `ProductWriteRequest` 只允许商品编辑字段，`@NotBlank`、`@Min`、`@Size` 等注解在进入业务代码前阻止明显非法数据。

DTO 校验不是最终安全边界：

- 前端校验只是体验优化，用户可以绕过前端直接调用 API。
- Service 仍要校验跨字段规则，例如优惠金额必须小于使用门槛。
- 数据库约束是最后一层保护，例如 SKU 唯一索引防止并发重复。

### 第四步：重点阅读 Service

Service 是后端最值得花时间看的地方。建议按“前置条件 → 查询 → 业务判断 → 写入 → 返回”给每个方法做流程图。

`@Transactional` 表示一个方法里的多次数据库操作要作为一个整体提交：全部成功才提交；出现需要回滚的异常就全部撤销。人工发券就是典型例子：模板库存增加、发放审计记录写入、用户优惠券批量写入必须保持一致。

阅读 Service 时重点关注：

- 是否检查了资源存在、状态、归属和权限？
- 是否区分了“客户端输入错误”和“资源状态冲突”？
- 是否有金额、库存、数量的边界检查？
- 多张表写入是否在同一个事务中？
- 并发请求会不会重复写入或超发？
- 返回的是 Entity 还是经过筛选的 VO？

### 第五步：最后看 Mapper 和 SQL

Mapper 是 MyBatis-Plus 访问数据库的接口。继承 `BaseMapper<T>` 后，就拥有常见的 `selectById`、`insert`、`updateById`、`deleteById`、`selectPage` 等方法。

`LambdaQueryWrapper` 可以理解为“用 Java 方法引用拼 SQL 条件”，例如：

```java
new LambdaQueryWrapper<Product>()
    .eq(Product::getStatus, 1)
    .like(Product::getName, keyword);
```

它表达的意思接近：

```sql
WHERE status = 1 AND name LIKE ?
```

优惠券库存使用了自定义条件更新 SQL。它把“状态必须 ACTIVE、库存不能超总量、固定有效期不能过期、库存加一”放在同一条 SQL 中，数据库会对这条更新提供原子性，避免两个并发请求都读到同一个剩余库存。

### 第六步：Entity 和 VO 分开看

Entity 是数据库内部模型，字段通常和表一致，可能包含 `passwordHash`、OpenID、角色等不应该返回给用户的内容。

VO 是返回给客户端的公开模型。比如消费端商品详情故意不返回 SKU、精确库存和后台状态；这是“返回字段白名单”，不是多余的复制。

## 3. 本项目各模块的阅读路线

### 3.1 应用启动和配置

入口是 `MallApplication`。`@SpringBootApplication` 会启动 Spring 容器，扫描 `com.aimall` 下的 Controller、Service、Mapper 和配置类。

- `SecurityConfig`：认证、角色权限、无状态 Session、401/403 JSON。
- `WebConfig`：本地开发 CORS 和 Long 转字符串序列化。
- `MybatisPlusConfig`：分页拦截器及每页最多 100 条的限制。
- `application.yml`：数据库、JWT、登录锁定和微信配置。

### 3.2 登录和身份认证

建议按这个顺序读：

1. `AuthController`：看注册、密码登录、微信登录、刷新、退出和当前用户接口。
2. `LoginRequest`、`RegisterRequest` 等 DTO：看输入校验。
3. `AuthService`：看密码校验、失败次数、账号锁定、Session 创建和刷新令牌轮换。
4. `JwtService`：看访问令牌如何签名、过期和解析。
5. `JwtAuthenticationFilter`：看每个请求如何从 `Authorization: Bearer ...` 恢复身份。
6. `SecurityConfig`：看哪些 URL 公开、哪些 URL 要登录、哪些 URL 要角色。

访问令牌 JWT 用来快速验证请求；刷新令牌是随机字符串，数据库只存 SHA-256 摘要，刷新时会撤销旧 Session 并创建新 Session。两者职责不同，不要把刷新令牌当成普通 JWT 使用。

### 3.3 商品和消费端商品

后台商品链路：


```text
ProductController -> ProductService -> ProductMapper -> product 表
```

消费端链路：

```text
ShopProductController -> ShopProductService -> ProductMapper -> product 表
```

两条链路共用商品表，但返回 VO 不同。消费端查询在 Service 层强制 `status = 1`，因此不能通过修改 URL 参数看到下架商品。

商品 `PUT` 是完整替换：请求体中的空图片和空描述会被规范化为 `NULL` 并显式写入数据库。这里不能简单换成默认 `updateById`，因为某些 ORM 默认会忽略 null，导致旧图片无法清除。

### 3.4 购物车

建议阅读：`CartController -> CartService -> CartItemMapper -> CartItem`。

购物车的用户 ID 从 JWT 取得；添加商品时需要再次查询商品，确认商品存在、已上架且有库存；同一用户和同一商品通过数据库唯一键保持一条购物车记录。

### 3.5 优惠券

优惠券是本项目最复杂的业务，建议拆成四条链路阅读：

1. 模板管理：`CouponTemplateController -> CouponTemplateService -> CouponTemplateMapper`。
2. 人工发券：`CouponGrantController -> CouponGrantService`，同时写 `coupon_grant` 和 `user_coupon`。
3. 我的优惠券：`UserCouponController -> UserCouponService`，只按 JWT 用户过滤。
4. 分享领取：`CouponShareController -> CouponShareService`，使用随机分享 token 的哈希、领取记录唯一键和条件库存更新。

模板状态是 `DRAFT -> ACTIVE -> DISABLED`。草稿可以完整编辑；启用后核心规则锁定；停用阻止继续发放，但不自动作废已经发给用户的券。

### 3.6 全局异常处理

`GlobalExceptionHandler` 相当于后端版的统一错误拦截器。Service 抛出有业务含义的异常，例如 `ProductNotFoundException` 或 `CouponGrantConflictException`；处理器把它们转换成稳定的 HTTP 状态码、错误码和中文消息。

这样 Controller 不需要在每个方法里重复 `try/catch`，前端也可以统一按 `code` 处理错误。

## 4. 一般后端开发流程：先写什么、后写什么

推荐采用“契约先行、垂直切片交付”的顺序：

1. 明确用户故事和状态：先写“谁在什么条件下做什么，成功和失败分别是什么”。
2. 设计数据库：确定表、字段、状态、唯一键、外键、金额精度和并发约束。
3. 更新 API 契约：在 `api/openapi.yaml` 中写 URL、请求、响应、错误码。
4. 写 DTO：把客户端可提交的字段和基础格式校验固定下来。
5. 写 Entity：让 Java 对象对应数据库表。
6. 写 Mapper：先使用 MyBatis-Plus 通用方法；涉及库存、幂等或锁时补充明确 SQL。
7. 写异常类型和全局映射：先定义失败语义，避免最后只能返回模糊的 500。
8. 写 Service：实现规则、权限边界、事务和数据转换。
9. 写 VO：只暴露客户端真正需要的字段，防止把内部字段原样返回。
10. 写 Controller：把 HTTP 参数接到 DTO/Service，保持薄层。
11. 写后端测试：先测 Service 业务规则，再测 Controller 的状态码、JSON 和权限。
12. 写前端 API 类型和页面：前端只依赖已经确定的 API 契约。
13. 做集成验收：启动数据库和后端，使用两个测试账号验证正常、重复、越权、过期、并发等场景。
14. 更新文档和项目记忆：记录改动、运行命令、已验证内容和未完成事项。

如果是前端主导的小功能，也可以记成一句话：先定数据和接口，再写后端业务，最后接页面；不要先把页面状态写死后再反推数据库规则。

## 5. 发生问题时如何定位

### 页面提示“服务器错误”

先看浏览器 Network：请求 URL、状态码、请求体和响应 JSON。再根据状态码定位：

- 400：DTO 或 Service 业务规则不通过。
- 401：没有 Bearer Token、Token 无效或刷新令牌失效。
- 403：已登录但角色不足，或账号被禁用。
- 404：资源不存在，或消费端访问了下架商品。
- 409：唯一键、库存、状态或幂等冲突。
- 500：查看后端日志中的异常类型和堆栈，不把服务器内部细节返回给用户。

### 数据库里没有预期数据

依次确认：

1. 请求是否真的到达 8080 端口。
2. Service 是否在事务中抛出了异常，导致整笔事务回滚。
3. 查询是否按当前用户或状态过滤掉了数据。
4. 是否连接了你以为的数据库；开发和生产配置可能指向不同实例。

### 权限问题

不要只看前端路由守卫。前端守卫只是隐藏页面，真正安全边界是 `SecurityConfig`、`JwtAuthenticationFilter` 和 Service 内的归属校验。

## 6. 前端开发者的学习建议

第一遍只追一条最短链路，例如商品列表；第二遍追登录；第三遍再读优惠券的事务和并发。阅读时每个方法只回答四个问题：输入是什么、查了什么、改了什么、输出和失败是什么。

遇到陌生注解，先看它改变了哪一件事：

- `@RestController`：类可以接收 HTTP 请求并把返回值序列化成 JSON。
- `@Service`：类交给 Spring 管理，其他类可以注入它。
- `@Mapper`：接口由 MyBatis 生成实现，用于数据库访问。
- `@Transactional`：把一组数据库操作放在同一个事务中。
- `@Valid`：触发 DTO 字段校验。
- `@PreAuthorize` 或 `SecurityConfig` 规则：限制调用者权限。

最后，注释里最有价值的不是重复语法，而是说明“为什么必须这样写”。例如“不能使用 updateById，因为它可能忽略 null”“用户 ID 必须来自 JWT，不能相信请求参数”“条件更新用于防止并发超发”。这些就是从前端转向全栈时最值得掌握的后端思维。
