本文档记录 AI Mall 当前版本的订单设计。业务范围是“线上下单、线下取货”，暂不接入真实支付和物流配送。每个实施阶段都要先确认方案，再修改代码、数据库或 API，并在阶段结束后补充测试和项目记忆。

## 一、当前业务范围

### 1. 用户能够做什么

```text
浏览上架商品
→ 加入购物车
→ 选择购物车商品并提交订单
→ 获得订单号和取货码
→ 到指定取货点线下付款
→ 出示取货码
→ 工作人员确认已取货
```

### 2. 当前不做什么

- 不做快递配送、物流公司、运单号和收货地址。
- 不接微信支付、支付宝或银行卡真实扣款。
- 不保存银行卡号、支付密码或任何支付敏感信息。
- 不做多门店库存调拨。
- 不做复杂订单拆单、分批取货或售后退款。

### 3. 第一版关键假设

- 暂时只有一个固定取货点。
- 取货点名称和地址由后端配置提供，创建订单时复制进订单快照。
- 线下取货时付款，因此下单不需要在线支付回调。
- 订单提交后锁定库存；取消订单或超时关闭时释放库存。
- 取货码由后端安全随机生成，只保存哈希，用户端只展示明文取货码。

如果未来增加多门店，只需要把固定配置替换成 `pickup_location` 表和门店选择接口；订单仍然保存取货点快照，不修改历史订单。

## 二、前端开发者需要先理解的三个概念

### 1. 订单不是购物车

购物车是“用户暂时想买什么”，可以随时增删改；订单是“某一时刻已经提交的购买意图”，提交后商品名称、价格、数量和取货信息必须固定。因此创建订单时必须复制商品快照，不能只保存 productId 后每次重新读当前商品价格。

### 2. 锁库存不是最终扣库存

订单创建时先把库存标记为被订单占用，避免多个用户同时下单超过库存；订单取消时释放；工作人员确认取货时才完成最终扣减。数据库需要区分 `stock` 和 `reserved_stock`，可售库存为 `stock - reserved_stock`。

### 3. 取货码是一次性凭证

取货码类似线下核销密码：用户把它展示给工作人员，后台输入或扫描后确认订单。它不能使用递增订单 ID，也不能把用户 ID 放进二维码明文；必须随机、不可猜、可一次性使用，并在数据库中保存哈希。

## 三、订单状态设计

### 1. 订单状态

| 状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| `PENDING_PICKUP` | 已下单，等待用户到店取货 | 用户查看、取消；后台确认取货 |
| `PICKED_UP` | 已线下付款并完成取货 | 只能查看 |
| `CANCELLED` | 用户或系统取消，库存已释放 | 只能查看 |

第一版不设置 `PAID`，因为付款发生在线下。订单金额仍然必须保存，作为工作人员收款依据和历史记录。

### 2. 状态流转

```text
PENDING_PICKUP ──用户取消──> CANCELLED
       │
       └────后台核销取货──> PICKED_UP
```

规则：

- 只有 `PENDING_PICKUP` 能取消或核销。
- 重复取消已经取消的订单按幂等成功处理。
- 重复核销已经取货的订单，在取货码正确时按幂等成功返回当前详情，不得重复扣库存；取货码错误仍返回核销错误。
- 已取消订单不能再核销。
- 状态切换必须带上旧状态条件，防止两个后台工作人员同时操作时重复成功。

## 四、数据模型设计

### 1. `mall_order` 订单主表

代码和 SQL 使用 `mall_order` 作为实际表名；下面的“订单主表”均指这张表。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 订单数据库主键 |
| `order_no` | 对外展示的订单号，唯一且不可猜测要求低于取货码 |
| `user_id` | 下单用户 |
| `status` | `PENDING_PICKUP`、`PICKED_UP`、`CANCELLED` |
| `pickup_location_name` | 取货点名称快照 |
| `pickup_location_address` | 取货点地址快照 |
| `pickup_code_hash` | 取货码哈希，绝不返回给前端 |
| `total_amount` | 下单时计算并保存的订单总金额 |
| `item_quantity` | 商品总件数快照，便于列表展示和统计 |
| `idempotency_key` | 用户本次提交生成的幂等键；同一用户重复提交同键时复用原订单 |
| `idempotency_payload_hash` | 商品 ID + 数量规范化后的 SHA-256 摘要；防止同一个键被改成另一组商品参数 |
| `cancelled_at` | 取消时间，可为空 |
| `picked_up_at` | 核销取货时间，可为空 |
| `created_at` | 下单时间 |
| `updated_at` | 最近修改时间 |

金额使用 `DECIMAL(10,2)`，Java 使用 `BigDecimal`。订单总金额由后端根据数据库商品价格计算，不能相信前端提交的 totalAmount。

建议索引：

- `UNIQUE(order_no)`：订单号不能重复。
- `INDEX(user_id, created_at)`：查询“我的订单”。
- `INDEX(status, created_at)`：后台按待取货/已取货筛选。
- `UNIQUE(pickup_code_hash)`：随机取货码哈希唯一，降低碰撞风险。

### 2. `order_item` 订单商品明细表

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 明细主键 |
| `order_id` | 所属订单 |
| `product_id` | 原商品 ID，可用于追溯 |
| `sku` | 下单时 SKU 快照 |
| `product_name` | 下单时商品名称快照 |
| `unit_price` | 下单时单价快照 |
| `quantity` | 下单数量 |
| `line_amount` | `unit_price * quantity` 快照 |
| `created_at` | 明细创建时间 |

订单明细不依赖商品当前状态展示历史订单。商品下架、改名或调价后，历史订单仍显示下单时内容。

### 3. 商品库存字段扩展

现有 `product` 表有 `stock`，第一版需要新增 `reserved_stock`，默认 0，且必须满足：

```text
0 <= reserved_stock <= stock
可售库存 = stock - reserved_stock
```

下单时使用条件更新：

```sql
UPDATE product
SET reserved_stock = reserved_stock + :quantity
WHERE id = :productId
  AND status = 1
  AND stock - reserved_stock >= :quantity;
```

返回更新行数为 1 才表示成功锁到库存；返回 0 表示商品下架、库存不足或并发请求已经占满库存。取消时使用条件更新减少 `reserved_stock`，并确保不会减成负数。

### 4. 暂不单独建支付表

当前线下付款不需要支付回调和第三方交易号，因此第一版不建 `payment` 表。订单只保存应收总金额，后台确认取货时由工作人员在线下收款。

未来接入在线支付时再增加：

- `payment_status`：待支付、已支付、支付失败、已退款。
- `payment` 支付尝试表和第三方交易号。
- 回调幂等键、签名验证和退款记录。

## 五、接口设计

### 1. 消费端接口

```http
POST /api/v1/orders/preview
POST /api/v1/orders
GET  /api/v1/me/orders
GET  /api/v1/me/orders/{orderId}
POST /api/v1/me/orders/{orderId}/cancellation
```

#### 订单预览

`POST /orders/preview` 只计算当前购物车选中商品的价格、库存可用性和取货信息，不写订单、不锁库存。它用于确认页面展示最终金额。

请求只提交购物车商品选择和数量，不能提交商品价格、订单总额、用户 ID 或订单状态。后端重新查询商品并计算金额。

#### 创建订单

`POST /orders` 在一个事务中完成：

1. 从 JWT 获取用户 ID。
2. 查询并校验购物车条目归属。
3. 重新读取商品价格、上架状态和库存。
4. 条件更新锁定全部商品库存。
5. 复制商品和取货点快照。
6. 生成订单号和取货码哈希。
7. 写入订单和订单明细。
8. 删除已经下单的购物车条目。
9. 返回订单详情和一次性明文取货码。

创建订单需要幂等键，例如 `clientRequestId`。同一用户用同一幂等键重复提交时返回第一次订单；参数不同则返回冲突，避免网络重试产生两笔订单。

#### 我的订单

查询条件必须同时带上 JWT 用户 ID 和订单 ID/分页条件。即使用户知道别人的 orderId，也只能得到 404 或“订单不存在”，不能看到对方的商品、金额和取货码。

#### 取消订单（已完成后端实现）

只允许取消 `PENDING_PICKUP`。取消和释放库存放在同一个事务中，先锁订单和商品，再按明细聚合数量释放 `reserved_stock`，最后使用状态条件更新保证并发安全。重复取消已经取消的订单按幂等成功处理；已取货订单返回 `ORDER_STATE_CONFLICT`。

### 2. 后台接口

```http
GET  /api/v1/admin/orders
GET  /api/v1/admin/orders/{id}
POST /api/v1/admin/orders/{id}/pickup-verification
```

- 列表和详情只允许 `SUPER_ADMIN`、`ADMIN`、`OPERATOR`。
- 核销接口接收路径订单 ID 和取货码，不接收客户端提交的新状态。
- 核销时后端先锁定订单行，再规范化输入并比较取货码 SHA-256 摘要；明文只存在于当前请求内，不写日志、不返回响应。
- 待取货订单核销时按商品 ID 升序锁商品，使用条件更新同时减少 `stock` 与 `reserved_stock`，随后用 `WHERE status = 'PENDING_PICKUP'` 把订单改为 `PICKED_UP` 并设置 `picked_up_at`。
- 已取货订单使用正确取货码时返回当前详情（幂等），错误取货码、已取消订单、库存不一致分别返回稳定的 409 业务错误码。

## 六、事务和并发规则

### 1. 创建订单事务

创建订单涉及商品库存、订单主表、订单明细、购物车四类数据，必须使用一个事务。任一步失败都回滚：不能出现“库存锁了但没有订单”或“订单创建了但库存没有锁住”。

多个商品锁定时，按 productId 升序处理，减少不同请求锁定顺序不一致导致的死锁概率。真实数据库测试要覆盖两个用户同时抢最后一件商品的场景。

### 2. 取消订单事务

取消时先用旧状态条件把订单从 `PENDING_PICKUP` 改为 `CANCELLED`，确认更新行数为 1 后释放明细对应的 `reserved_stock`。如果订单已经被核销或取消，条件更新返回 0，不能再次释放库存。

### 3. 核销事务

核销时先锁订单并验证取货码。已取货订单的正确重复请求直接返回，不进入库存写入；待取货订单才会按固定顺序锁商品、结算库存并用旧状态条件更新订单。两个工作人员同时核销同一个订单时，订单行锁会串行化请求，最多一次库存结算，后到请求只能得到幂等结果或明确错误。

## 七、取货码安全设计

- 当前使用 `SecureRandom` 从排除易混淆字符的 32 个字符集中生成 8 位取货码，约有 40 bit 的随机空间；订单价值或攻击面扩大后应增加长度并补充错误次数限制。
- 推荐展示数字/大写字母混合码；如果后续做扫码，二维码内容仍只放随机 token。
- 数据库只保存 SHA-256 哈希，不保存明文。
- 用户创建订单响应中只返回一次明文取货码；订单详情接口不重复返回明文，可以返回“已生成取货码”的提示。
- 日志不能输出明文取货码、完整二维码内容或用户隐私。
- 核销成功后取货码不能再次触发库存写入；正确重复提交只用于幂等确认，不能把已取货订单恢复或再次扣库存。

## 八、错误码建议

| 错误码 | HTTP | 场景 |
| --- | --- | --- |
| `ORDER_NOT_FOUND` | 404 | 订单不存在或不属于当前用户 |
| `ORDER_STATE_CONFLICT` | 409 | 当前状态不允许取消/核销 |
| `ORDER_STOCK_INSUFFICIENT` | 409 | 创建订单时商品可售库存不足 |
| `ORDER_INVENTORY_CONFLICT` | 409 | 取消释放或取货结算时库存数据不一致 |
| `ORDER_IDEMPOTENCY_CONFLICT` | 409 | 幂等键对应的请求参数不同 |
| `ORDER_PICKUP_CODE_INVALID` | 409 | 取货码错误或已失效 |
| `ORDER_PREVIEW_CHANGED` | 409 | 预览后商品价格/库存已变化，需要重新预览 |

错误响应继续使用现有 `ErrorResponse` 结构，前端按 `code` 分支，不依赖中文 message 判断逻辑。

### 第 6 阶段：完整验收

覆盖正常下单、库存不足、并发抢购、重复提交、取消释放、重复取消、错误取货码、重复核销、越权访问、商品下架、价格变化、优惠券过期和数据库事务回滚。

## 十、第一版推荐方案和取舍

推荐“线下取货时付款 + 单取货点 + 订单锁库存 + 后台一次性核销”。

优点：

- 本地可以完整测试，不需要商户号、证书、HTTPS 回调和真实扣款。
- 订单状态少，前端页面容易理解。
- 商品和订单快照清楚，后续接在线支付时可以继续扩展。
- 库存、幂等和权限等真正的后端难点仍然得到锻炼。

缺点：

- 下单后库存会被占用，需要取消或超时释放机制。
- 线下收款依赖工作人员操作，暂时没有自动支付凭证。
- 单取货点配置不适合立即扩展多门店。

## 十一、本地测试方式

本地不需要真实支付账号。使用两个或多个测试用户，准备少量商品，按以下顺序验收：

1. 用户 A 下单，确认购物车条目、订单主表和订单明细快照正确。
2. 修改商品名称/价格，确认历史订单仍显示原快照。
3. 用户 B 同时抢最后一件商品，确认只有一个请求成功。
4. 用户 A 取消订单，确认库存重新可售。
5. 工作人员使用正确取货码核销，确认状态变成 PICKED_UP。
6. 再次使用同一取货码，确认返回当前已取货详情且库存不重复变化；使用错误码确认返回 `ORDER_PICKUP_CODE_INVALID`。
7. 用户 B 尝试读取用户 A 的订单，确认返回 404/无权访问。
8. 重复提交同一个幂等键，确认只产生一笔订单，第二次 `pickupCode` 为空且 `replayed=true`；同键不同商品参数返回 `ORDER_IDEMPOTENCY_CONFLICT`。
9. 取消待取货订单，确认状态变成 `CANCELLED`、`reserved_stock` 恢复；重复取消不再次改变库存；已取货订单取消返回 `ORDER_STATE_CONFLICT`。
10. Admin 账号查询订单列表和详情，确认状态筛选、订单号/客户 ID 筛选、客户摘要和商品快照正确，且匿名访问返回 401。
11. Admin 使用正确取货码核销，确认状态变成 `PICKED_UP`、`stock` 和 `reserved_stock` 各减少对应数量；库存不足时确认整个事务回滚。
12. Admin 浏览器打开 `/orders`，确认菜单、筛选、分页和详情抽屉正常；核销按钮和弹窗待前端接入后再做浏览器验收。

本机已完成一条真实接口链路验收：注册/登录临时用户、加入商品、创建订单、重复创建、同键改参数、读取订单详情；结果分别为 201、200、200、200、409、200。验收产生的临时订单、购物车、会话、用户和预留库存均已清理，商品库存恢复原值。

本机另完成取消链路验收：下单前 `reserved_stock=0`，下单后为 2，首次取消后恢复为 0，重复取消后仍为 0；临时用户、订单和会话已清理。

真实微信支付属于后续独立阶段，必须在有商户配置、HTTPS 回调环境和专门测试账号后再做，不能用本地模拟结果代替真实支付验收。

## 十二、面试回答

> 本项目采用线上下单、线下取货的轻量订单模型。订单创建时由后端重新读取商品价格并保存商品快照，通过条件更新锁定库存；取消订单释放库存，工作人员使用一次性随机取货码完成核销。用户 ID 来自 JWT，订单查询做归属校验；金额、库存、幂等和状态转换都由后端和数据库共同保证。由于暂不接真实支付，本地可以完整验证下单、库存和取货链路，在线支付作为后续可插拔扩展。
