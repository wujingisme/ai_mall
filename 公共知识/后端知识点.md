# 后端知识点

只记录项目中已经实际使用的后端知识，方便复习和面试。

## 一、微信登录与权限

### 请求流程

```text
小程序登录 → 后端确认微信身份 → 签发商城 Token
→ 请求携带 Token → 后端解析用户 ID 和角色 → 判断是否允许访问
```

### 权限是什么

- 认证：确认“你是谁”。
- 权限：确认“你能做什么”。
- 本项目的角色包括顾客、运营人员、管理员和超级管理员。
- `SecurityConfig` 统一规定接口允许哪些角色访问。例如普通顾客不能调用后台发券接口。
- 前端隐藏按钮只改善界面，不能保证安全；最终必须由后端拦截。

### 分层

- Controller：接收请求和返回结果。
- Service：处理登录、账号状态等业务规则。
- Mapper：读取或修改用户、会话数据。
- Entity：对应数据库表中的数据。

### 面试简答

> 系统使用 Spring Security 在后端统一鉴权。Token 用于确认身份和角色，接口再按角色授权；前端菜单控制不作为安全边界。

## 二、人工发券与事务

### 请求流程

```text
管理员提交发券请求
→ Controller 接收参数和管理员身份
→ Service 校验用户、模板、库存和限领
→ Mapper 更新模板并写入发放记录、用户优惠券
→ Controller 返回发放结果
```

### 为什么分层

- Controller 不堆业务规则，接口变化时更容易维护。
- Service 集中处理“能不能发、发几张”等业务规则。
- Mapper 只负责数据库操作，便于替换查询方式和测试业务逻辑。

### 事务是什么

事务保证一组数据库操作“全部成功或全部撤销”。人工发券需要同时：

1. 增加模板已发行数量。
2. 写入发放记录。
3. 创建用户优惠券。

任何一步失败，`@Transactional` 都会撤销本次全部修改，避免数量增加了但用户没有收到券。

### 并发和幂等

- 条件更新保证多人同时发券时不会超过模板总量。
- 幂等键保证同一次请求重复提交时不会重复发券。
- 用户券保存发放时的规则快照，模板以后变化也不会影响已有权益。

### 面试简答

> 人工发券在一个事务中完成额度预占、限领检查、审计记录和用户券创建；条件更新防止并发超发，幂等键防止重复提交，任一步失败都会整体回滚。

## 三、后台用户管理

### 核心做法

- 后台接口先由 Spring Security 判断管理员角色，再由业务层确认目标确实是 CUSTOMER。
- 返回 `wechatBound` 布尔值，不返回 OpenID 等微信身份字段，满足“能管理”与“少暴露敏感信息”。
- 启用/停用是独立接口，重复执行不会改变最终状态。

### 面试简答

> 用户管理采用后端角色鉴权和业务对象校验双重保护；页面只展示必要摘要，微信身份信息不出现在管理接口响应中，状态变更使用明确的启用和停用操作。

## 四、优惠券分享领取

### 核心做法

- 分享链接只带随机凭证，数据库只保存凭证摘要，避免泄露用户 ID 和优惠规则。
- 公开解析只返回展示信息；真正领取必须登录，并由后端重新检查有效期、库存、限领和是否本人。
- `(分享记录, 领取用户)` 唯一约束防止同一个用户重复领取；领取成功才创建用户券。

### 面试简答

> 分享功能把展示和领取分开：解析接口可以公开，领取接口必须鉴权；随机凭证只存哈希，数据库唯一约束和事务共同保证防重复、不过量发券。

## 五、阅读后端代码和开发顺序

### 推荐阅读顺序

1. 先看功能设计，确认用户故事、状态和失败场景。
2. 再看 `database/schema.sql`，理解表、字段、唯一键和外键。
3. 看 `api/openapi.yaml`，确认前后端约定的 URL、请求和响应。
4. 从 Controller 找入口，再跟到 Service、Mapper、Entity，最后看 VO 和异常处理。
5. 阅读 `SecurityConfig` 和 `JwtAuthenticationFilter`，确认登录和角色权限不是只靠前端页面控制。
6. 最后看测试，理解每个正常、非法、越权、重复和并发场景为什么必须存在。

### 一个请求的开发流程

```text
需求/状态
→ 数据库表和约束
→ OpenAPI 契约
→ DTO 输入校验
→ Entity 数据模型
→ Mapper 查询/更新
→ Service 业务规则和事务
→ VO 输出白名单
→ Controller HTTP 入口
→ 测试
→ 前端 API 和页面
```

### 面试简答

> 我会先确定业务状态和数据约束，再定义 OpenAPI 契约；然后按 DTO、Entity、Mapper、Service、VO、Controller 的分层实现，并先补业务规则和权限测试，最后让前端接入稳定的接口。这样可以避免先把页面状态写死，再被迫反推数据库和并发规则。

## 六、订单第 1 阶段：预览与我的订单只读查询

### 请求流程

```text
前端提交商品 ID + 数量
→ Controller 从 JWT Authentication 取得当前用户 ID
→ DTO 校验数量和商品 ID
→ OrderService 查询当前用户购物车
→ OrderService 重新查询商品最新价格、上架状态和库存
→ 计算行金额/总金额，返回取货点配置
```

### 为什么预览不相信前端金额

- 前端传来的价格、总额可能是旧缓存，也可能被人为修改，所以请求只允许提交商品 ID 和数量。
- Service 必须同时按 `user_id + product_id` 查询购物车，防止用户预览不属于自己的购物车商品。
- 商品调价、下架或库存变化会在预览时立即反映；库存不足返回 409，提示前端刷新后重试。
- 第 1 阶段没有数据库写入，因此不会产生“预览失败却留下订单”或“预览占住库存”的副作用。

### 我的订单为什么要做归属条件

`GET /api/v1/me/orders` 和详情查询都会把 JWT 用户 ID 放进 SQL 条件。详情查不到时统一返回 `ORDER_NOT_FOUND`，不区分订单不存在还是属于别人，避免通过订单 ID 探测其他用户数据。

### 面试简答

> 订单预览接口只接收商品选择，不接收金额和用户 ID；后端从 JWT 确认用户，再读取购物车和商品表的最新数据计算金额。我的订单查询始终带用户归属条件，详情未找到统一返回 404。当前阶段不写订单、不锁库存，后续创建订单时再用事务处理快照、幂等和库存预留。

## 七、订单第 2 阶段第一小步：预留库存基础

### 请求和数据流

```text
商品总库存 stock + 待取货订单预留 reserved_stock
→ 购物车/商品列表/订单预览统一计算可售库存
→ 后台修改总库存时校验不能低于 reserved_stock
```

### 为什么这样设计

- `stock` 表示商品总库存，`reserved_stock` 表示已经被未完成订单占用的数量；当前可售库存是两者之差。
- 只改库存口径，不提前锁库存；真正下单时才会在事务中使用条件更新增加 `reserved_stock`。
- 数据库 `CHECK (reserved_stock <= stock)` 和 Service 校验一起保护不变量：数据库防止遗漏路径，Service 给 Admin 返回可理解的 409 错误。
- 购物车中已有商品不会因为预留而被删除，只会变成不可购买或显示较少的可售数量。

### 涉及分层

- Entity 增加 `reservedStock` 字段，映射数据库列。
- Cart/Shop/Order Service 统一使用可售库存，避免不同页面各自计算出不同结果。
- Product Service 在完整替换库存前检查已有预留，GlobalExceptionHandler 返回 `PRODUCT_STOCK_CONFLICT`。
- 当前还没有创建订单、库存锁定、取消释放或取货核销事务；这些属于后续小步。

### 面试简答

> 我把总库存和订单预留库存分开，商品可售量统一按 `stock - reserved_stock` 计算。数据库 CHECK 约束负责最终兜底，Service 负责给后台明确的冲突提示；真正的预留会在创建订单事务中用条件更新完成，避免并发超卖。

## 八、订单第 2 阶段第二小步：正式创建订单

### 从前端请求到数据库的流程

```text
前端提交购物车商品 ID/数量 + clientRequestId
→ Controller 从 JWT 取得用户 ID，并校验请求格式
→ OrderService 锁住用户幂等键对应的订单记录
→ 按 productId 升序锁住购物车行和商品行
→ 重新校验购物车归属、商品上架状态和可售库存
→ 条件增加 product.reserved_stock
→ 写 mall_order 主表和 order_item 商品快照
→ 删除本次已经下单的购物车行
→ 返回订单详情和一次性明文取货码
```

### 为什么价格、名称和库存不能由前端决定

- 前端只能提交 `productId` 和 `quantity`，不能提交 `price`、`totalAmount`、SKU、用户 ID 或订单状态。
- Service 锁定商品后从数据库读取最新价格、名称和 SKU，金额用 `BigDecimal` 重新计算。
- 订单明细保存下单瞬间的商品快照；以后商品改名、调价或下架，历史订单仍然显示原来的内容。
- 可售库存统一是 `stock - reserved_stock`。数据库条件更新返回 0 时，即使前面读取过库存，也必须按并发冲突拒绝。

### 事务、并发和幂等

- `@Transactional` 把幂等查询、购物车锁、商品锁、库存预留、订单写入、明细写入和购物车删除放在一起；任一步失败都会回滚，避免只扣库存不生成订单。
- 多商品订单按 `productId` 升序取锁，减少两个订单以不同顺序锁商品导致死锁的概率。
- `clientRequestId` 是一次“点击提交”的唯一键。相同用户、相同键、相同商品参数重试时返回原订单，不会重新占库存；相同键但商品参数不同返回 `ORDER_IDEMPOTENCY_CONFLICT`。
- 取货码使用 `SecureRandom` 生成，数据库只保存 SHA-256 摘要；第一次创建响应返回明文，重试和详情接口不再返回明文。

### 这一步改了哪些后端层

- DTO：定义商品选择和幂等键，并在 Controller 层拦截空列表、非法 ID、数量过大和非法键字符。
- Mapper：新增 `SELECT ... FOR UPDATE` 行锁和条件预留库存 SQL。
- Service：负责金额、快照、事务、并发锁顺序和重试语义。
- Entity/数据库：订单主表增加 `idempotency_payload_hash`，商品表使用已有 `reserved_stock`。
- VO/OpenAPI：创建响应区分首次创建的 `pickupCode` 和重试的 `replayed`。
- GlobalExceptionHandler：把同键不同参数转换为 HTTP 409，前端按错误码处理，不依赖中文提示。

### 面试简答

> 创建订单不是简单插入一行数据，而是一个事务：后端从 JWT 确认用户，锁购物车和商品，按数据库价格计算金额，条件预留库存，再保存订单和商品快照并删除已下单购物车。客户端幂等键解决网络重试，取货码只存哈希并只在首次响应返回；任一步失败都会回滚，防止库存和订单不一致。

## 九、订单前端提交的配合方式

前端确认订单页不自行计算最终金额，也不把金额当成创建请求参数。页面先调用预览接口展示后端结果，点击提交时只发送商品 ID、数量和 `clientRequestId`，由后端再次校验购物车、价格和库存。

页面在一次提交生命周期内保存同一个 `clientRequestId`。如果网络超时但用户再次点击，后端会把它识别为同一次请求；如果库存或购物车已经变化，页面重新加载预览并生成新键。提交按钮在请求期间禁用，避免普通的连续点击。

首次创建成功时页面显示取货码和订单号；订单详情接口不会返回取货码，所以取货码不能依赖详情页恢复，也不能通过 URL 传递。前端类型、API 客户端和页面状态必须与 `api/openapi.yaml` 中的 `OrderCreateResponse` 保持一致。

### 面试简答

> 前端只负责收集用户选择、展示后端预览结果和保存一次提交的幂等键，不负责决定价格或库存。提交成功后只在首次响应展示取货码，订单详情继续使用后端快照；这样前端刷新和网络重试不会改变订单金额或重复扣占库存。

## 十、订单取消与库存释放

### 请求流程

```text
用户点击取消
→ Controller 从 JWT 取得用户 ID 和路径订单 ID
→ Service 用 user_id + order_id 加 FOR UPDATE 锁订单
→ 检查状态必须是 PENDING_PICKUP
→ 读取订单商品快照，按 productId 聚合数量
→ 按 productId 升序锁商品并条件减少 reserved_stock
→ 条件更新订单为 CANCELLED，写入 cancelled_at
→ 返回取消后的订单详情
```

### 为什么不能直接改订单状态

订单创建时已经占用了商品的预留库存。如果只把订单改成 `CANCELLED` 而不释放库存，商品会一直显示少卖几件，最终形成库存泄漏。因此订单状态变化和库存释放必须在同一个 `@Transactional` 事务中：库存释放失败时订单状态也回滚。

### 并发和幂等

- 订单行先加锁，取消和未来的后台核销不会同时操作同一订单。
- 商品按 ID 升序加锁，并使用 `reserved_stock >= quantity` 条件更新，避免重复释放变成负数。
- 已取消订单重复调用直接返回当前快照，不再次访问商品库存；已取货订单返回 `ORDER_STATE_CONFLICT`。
- 商品删除前也要锁商品行并检查 `reserved_stock`。有预留时拒绝删除，否则订单明细的外键可能变成 `NULL`，系统将失去释放库存的依据。

### 面试简答

> 取消订单是订单状态和库存的联合事务，不是单纯把状态字符串改成 CANCELLED。后端先锁住用户自己的订单，再按订单明细锁商品并释放 reserved_stock，最后带旧状态条件更新订单；重复取消幂等，已取货订单拒绝，任一步失败整体回滚。

## 十一、Admin 订单列表和详情查询

### 请求流程

```text
Admin 页面携带后台 JWT
→ Spring Security 校验 ADMIN/OPERATOR/SUPER_ADMIN 角色
→ AdminOrderController 接收分页和筛选参数
→ AdminOrderService 在 mall_order 分页查询
→ 批量读取本页涉及的 mall_user 客户摘要
→ 读取 order_item 商品快照
→ 返回 Admin 专用 VO
```

### 为什么不能直接复用“我的订单”接口

- “我的订单”必须从 JWT 取得用户 ID，只能查当前用户；Admin 订单查询需要查看全部客户订单，归属条件不同。
- 单独的 Admin Controller 和 VO 可以明确返回 `userId`、用户名和显示名称，同时编译期排除密码摘要、微信 OpenID、取货码哈希等敏感字段。
- 商品名称、SKU、单价和数量必须从 `order_item` 快照读取；商品后来改名或下架时，历史订单仍然保持下单时的内容。

### 分页和 N+1 查询

列表先把状态、订单号、客户 ID 条件交给数据库，再执行分页；拿到当前页订单后收集所有 userId，一次 `selectBatchIds` 批量读取客户，避免每一行订单都单独查一次用户表。这个“先分页、后批量补齐”的顺序兼顾性能和代码可读性。

### 权限和异常

- `/api/v1/admin/orders/**` 由 Spring Security 统一限制后台角色；前端隐藏菜单不能替代服务端权限。
- 非法状态筛选返回 `ORDER_RULE_INVALID`（400）；订单不存在返回 `ORDER_NOT_FOUND`（404）。
- 查询接口不修改订单状态和库存，取货核销会在后续独立事务中完成。

### 面试简答

> 我把消费者订单查询和后台订单查询拆成两个边界：消费者按 JWT 做数据归属，后台按角色查看全部订单。Admin 列表先在数据库分页，再批量加载客户摘要，详情读取订单商品快照；响应使用专用 VO，避免把密码、OpenID 和取货码哈希带到前端。

## 十二、后台订单取货码核销与库存结算

### 请求流程

```text
Admin 页面提交订单 ID + 取货码
→ Spring Security 校验后台 JWT 和 ADMIN/OPERATOR/SUPER_ADMIN 角色
→ AdminOrderController 校验请求体格式
→ AdminOrderService 开启事务并锁定 mall_order 订单行
→ 规范化取货码、计算 SHA-256，与数据库摘要做常量时间比较
→ 已取货订单：正确码直接返回详情（幂等）；错误码拒绝
→ 待取货订单：读取 order_item，按 productId 聚合数量
→ 按 productId 升序锁定商品行，条件减少 stock 和 reserved_stock
→ 条件更新订单状态为 PICKED_UP，并写入 picked_up_at
→ 返回后台订单详情
```

### 为什么不能把取货码明文存进数据库

- 用户首次创建订单时才拿到明文取货码，订单详情和后台订单列表都不会再次返回它。
- 数据库只保存 SHA-256 摘要。店员输入后，后端把输入规范化为大写，再计算摘要比较；日志中也不记录输入值。
- DTO 只允许 8 位、排除 `0/1/I/O` 的字符，Service 再做一次同样的防守性校验，避免未来出现绕过 Controller 的调用入口。
- 当前正确重复核销会返回已取货详情，不会再次扣库存；错误码仍返回 `ORDER_PICKUP_CODE_INVALID`。

### 为什么核销和库存必须是一个事务

订单创建时，`reserved_stock` 代表“已经被待取货订单占用”，`stock` 仍代表仓库总量。实际取货时要把这部分从两种库存中同时移除：

```text
核销前：stock = 10，reserved_stock = 2，可售 = 8
核销 2 件后：stock = 8，reserved_stock = 0，可售 = 8
```

如果库存更新成功但订单状态更新失败，事务会整体回滚；如果商品不存在、数量不一致或条件更新返回 0，也会回滚，避免出现“订单显示已取货但库存仍被占用”或“库存扣了但订单还待取货”。

### 锁和幂等怎么配合

- 先锁订单行，两个店员同时核销同一订单时会串行执行；后到请求能看到前一个请求的最新状态。
- 多商品订单再按 `productId` 升序锁商品，减少不同请求按不同顺序拿锁造成死锁的概率。
- 商品库存 SQL 同时检查 `stock >= quantity`、`reserved_stock >= quantity` 和 `reserved_stock <= stock`，Service 不能只相信之前读取到的数字。
- 订单状态更新仍带 `WHERE status = 'PENDING_PICKUP'`，数据库层再做一次并发兜底。任何更新行数不是 1 都会抛出冲突异常。

### 这一步改了哪些后端层

- DTO：新增 `PickupVerificationRequest`，负责 JSON 字段、长度和字符集校验。
- Controller：新增后台 POST 核销入口，取货码不进入日志。
- Service：负责哈希验证、状态判断、明细聚合、事务边界、锁顺序和幂等语义。
- Mapper：新增订单 `FOR UPDATE`、条件状态更新和商品库存结算 SQL。
- ExceptionHandler：把错误取货码映射为 409 `ORDER_PICKUP_CODE_INVALID`，状态不允许映射为 `ORDER_STATE_CONFLICT`，库存数据不一致映射为 `ORDER_INVENTORY_CONFLICT`。
- OpenAPI：同步接口路径、请求体和 200/400/401/403/404/409 响应契约。

### 面试简答

> 后台核销不是简单把订单状态改成 PICKED_UP。后端先用 Spring Security 验证后台角色，再锁订单并比较取货码哈希；待取货订单按固定顺序锁商品，使用条件 SQL 同时减少 stock 和 reserved_stock，最后带旧状态条件更新订单。整个流程放在一个事务里，库存或状态任一步失败都会回滚；正确重复核销只返回当前详情，不会重复扣库存。
